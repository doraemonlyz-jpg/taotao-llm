1 · Tokenizer 在做什么 · 为什么不能跳过

所有现代 LLM 都做这两步映射：

"Hello, 世界! 🌏"
        ↓ tokenizer.encode
[15496, 11, 220, 161, 116, 244, 30298, 0, 220, 8582, 234, 235]
        ↓ model.forward · embedding + transformer
[15496 → "Hello"   prob 23%
            "world" prob 19%
            ...]
        ↓ tokenizer.decode
"Hello, 世界! 🌏 world..."

tokenizer 不是模型的一部分 · 它是模型外面的一层确定性查表。但它的设计直接决定四件大事：

设计选择影响
vocab_sizeembedding 矩阵 = vocab × n_embd · 直接占参数 / 显存
分词粒度同一句话的 token 数 → 训练 / 推理 cost · 上下文够不够用
byte-level vs not要不要处理 UNK · 中日韩泰阿等语言能不能不掉精度
special tokenschat template · function call · system prompt 怎么标

为什么不能跳过

面试官常问 "为什么 GPT-4 中文比英文贵"。如果你答 "因为中文字符多" · 你已经答错了 · 因为 GPT-4 用的是 byte-level · 一个英文字符 = 1 byte = 0.25 token (约) · 一个中文字符 = 3 byte ≈ 1-2 token。是 byte 数差异。

2 · 五种粒度 · char / word / subword / byte / pixel

粒度vocab序列长OOV例
character~100-10k很长稀有 unicode本项目 phase 1 nanoGPT
word50k-500k+很短新词 / typoword2vec · GloVe
subword (BPE/WP/Uni)10k-100k中取决于实现主流 LLM
byte-level≥256偏长从不GPT-2/3/4 · Llama-3
pixel / image patch———多模态 · ViT 路线

为什么 char 不够好

phase 1 我们用了 65 字符的 char-level · loss 能从 4.2 降到 1.5 · 但 vocab 太小有几个根本缺陷：

  • 序列长 4-5 倍：同样的内容 · char 序列 ≈ 5× BPE 序列 · 训练慢 · context 浪费
  • 每个 token 信息量太低：一个 token 只承载 1 字节信息 · attention 不得不学很长距离的依赖才能拼出一个词
  • 多语言外推差：中日韩字符不在 ASCII 65 内 · 完全编不动

为什么 word 也不行

"unhappy" / "happiness" / "happily" 在 word-level 是三个完全独立的 token · 模型学不到它们共享 "happy" 这个语义根。 而且新词 / 拼写错 / 专有名词必然 OOV · 退化成 <UNK> · 信息损失。

subword 是甜点

"unhappy" → ["un", "happy"] · "happiness" → ["happi", "ness"] · 共享了 "happy" 词根。 vocab 控制在 30k-100k 量级 · 序列长度可控 · 不用 UNK · 这就是 BPE / WordPiece / SentencePiece 的共同 motivation。

3 · BPE 算法 · 用 30 行 Python 自己写一遍

BPE = Byte-Pair Encoding · 1994 年的数据压缩算法 · 2016 年 Sennrich 把它搬到 NMT · 然后 GPT-2 把它做成 LLM 默认。

算法

初始化：vocab = 所有 base 单元（byte 或 char）
循环 N 次：
  1. 统计当前 token 序列里所有相邻 pair 的频次
  2. 取频次最高的 pair (a, b) · 给它一个新 id
  3. 把序列里所有 (a, b) 替换为新 id
输出：merges 列表（决定 encode 顺序）+ vocab 表

看 nano/bpe.py 的核心 30 行

def train(text: str, vocab_size: int) -> "BPE":
    ids = list(text.encode("utf-8"))         # base = 256 字节
    merges = {}
    vocab = {i: bytes([i]) for i in range(256)}
    for i in range(vocab_size - 256):
        counts = Counter(zip(ids, ids[1:]))  # 数 pair
        pair, _ = max(counts.items(), key=lambda kv: kv[1])
        new_id = 256 + i
        ids = _merge(ids, pair, new_id)      # 序列里替换
        merges[pair] = new_id
        vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
    return BPE(merges=merges, vocab=vocab)

就这。我们的 nano/bpe.py 完整版 ≈ 130 行 · 多出来的是 encode / decode / save / load + 注释。

encode 时为什么要用 "id 最小的 merge 优先"

训练时合并顺序 = 频次顺序。encode 时你拿到一段新文本 · 它里面可能有多个可合并的 pair · 此时按训练顺序（id 升序）从最早学到的 merge 开始套 · 才能跟训练时的切分保持一致。 看 nano/bpe.py 的 encode()：

while True:
    counts = _get_pair_counts(ids)
    applicable = [(self.merges[p], p) for p in counts if p in self.merges]
    if not applicable: break
    _, pair = min(applicable, key=lambda x: x[0])  # id 最小 = 学得最早
    ids = _merge(ids, pair, self.merges[pair])

坑

朴素 encode 是 O(N²) · 对长文本会慢。HF 的 Rust 实现用 trie / 双向链表把它降到 O(N log N) · 实测我们 nano 1MB 训了 34 秒 · HF 0.2 秒 · 170× 差距。教学版重看懂 · 工业版重跑得动。

4 · Byte-level BPE · 永远没有 UNK

朴素 BPE 在字符上做。如果训练语料里没出现过 "𓀀" · 推理时遇到它就只能 UNK。

Byte-level BPE 直接在 UTF-8 byte 上做。任何 Unicode 字符都能拆成 1-4 个 byte · base vocab 256 个 byte 永远覆盖。推理时不可能 OOV。

UTF-8 速记

字符范围byte 数例
U+0000 – U+007F (ASCII)1"a" → 0x61
U+0080 – U+07FF2"é" → 0xC3 0xA9
U+0800 – U+FFFF (大部分中日韩)3"中" → 0xE4 0xB8 0xAD
U+10000 – U+10FFFF (emoji / 古文字)4"🌏" → 0xF0 0x9F 0x8C 0x8F

所以一个中文字符 = 3 byte = 起始 3 token（在词表把它合并掉之前）。这就是中文吃亏的根本原因（详见第 7 节）。

验证 byte-level 不会 UNK

看 tests/test_bpe.py 的 test_special_chars_no_unk：

bpe = BPE.train(CORPUS_MIX, vocab_size=320)
weird = "\x00\x01\x02 ZWJ‍ NBSP\xa0 emoji 👨‍💻 中"
assert bpe.decode(bpe.encode(weird)) == weird   # ✓ 完美 roundtrip

5 · Pre-tokenization · GPT-2 那条出名的 regex

纯 byte-level BPE 有一个尴尬问题：合并是跨词的。

# 不预切的 BPE 会学到的离谱合并
("e",  " ") → "e "      # "the" 末尾 + 下个空格 = 一个 token
(" ", "t")  → " t"      # 空格 + "t" 开头 = 一个 token

结果："the" 出现位置不同时被切成不同 id · 模型要重学每个上下文。 解决：先用 regex 把文本切成有意义的边界单位（word-ish）· 再在每个单位内做 BPE。

GPT-2 的 regex（industrial/tokenizer/train_hf.py 同款）

'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}+|\p{N}{1,3}|
 ?[^\s\p{L}\p{N}]++[\r\n]*|\s*[\r\n]|\s+(?!\S)|\s+

看着像天书 · 拆开就是六条规则：

  1. 's 've 'll 'd 'm 't 're → 单独切（英文常见缩写）
  2. ?[非字母非数字]?字母+ → 一个英文词（前面可带一个空格 / 标点）
  3. 数字{1-3} → 数字串切成最多 3 位
  4. ?[符号]+ → 连续符号
  5. \s*[\r\n] → 空白 + 换行
  6. \s+ → 任何剩下的空白

这套切完后 · " the" 永远是一个 unit · " The" 又是一个 unit。BPE 在 unit 内学合并 · 跨 unit 不会合 · 解决了 token 不一致问题。

为什么数字限 3 位

"12345" 跟 "12346" 的语义几乎一样 · 但作为整 token 会爆炸性扩词表。切成 "123" + "45" 让模型学数字组合规律 · vocab 才控制得住。GPT-4 改成 1 位 · Llama-3 也是 1 位。

6 · WordPiece / Unigram · BPE 的两个亲戚

算法合并准则谁在用特点
BPE挑频次最高 pairGPT-2/3/4 · Llama · Mistral · Qwen简单 · 主流
WordPiece挑能让 likelihood 最大化的 pairBERT · DistilBERT · ElectraBPE 的一个变种 · 数学更优
Unigram反向：先大词表 · 不断剪掉对 likelihood 贡献最小的 tokenSentencePiece (T5 / mBART)能给出多种切分概率 · 适合 subword regularization

WordPiece 的微妙差异

# BPE 选 max(count(a, b))
# WordPiece 选 max( count(a, b) / (count(a) * count(b)) )
# 物理意义：让 (a, b) 同时出现的"惊讶程度"最大

实测差异不大。GPT 系列选 BPE 的原因是简单 + 跟 byte-level 配合好。BERT 用 WordPiece 是 Google 历史选择。

Unigram 的牛逼之处：可以采样切分

同一个词可能有多种合理切分 · Unigram 给每种切分一个概率 · 训练时随机采一种 · 起到正则化作用（类似 dropout）。研究显示对低资源语言提升明显。日常 LLM 不太用。

8 · 特殊 token · BOS / EOS / chat template

裸 BPE 只有自然语言 token。但要做 chat 模型 · 你必须能分隔不同的对话角色 · 这就是特殊 token：

token用途常见名字
BOS (begin)序列开始<s> · <|begin_of_text|>
EOS (end)序列结束 · 也是 generate 的停止信号</s> · <|endoftext|>
PADbatch 内对齐到等长<|pad|> · 也常复用 EOS
UNK未知 token (byte-level 用不到)<unk>

FIM (fill-in-middle)code 模型补全用<FIM_PREFIX> 等
Tool callfunction calling<|tool_call|> · <|tool_result|>

chat template · Llama-3 同款

<|begin_of_text|><|start_header_id|>system<|end_header_id|>

<|start_header_id|>user<|end_header_id|>

9 · vocab_size 怎么选 · 小模型 vs 大模型

这是个 tradeoff · 没有银弹。但有几条经验：

vocab典型场景权衡
~1k本书 nano · 教学序列超长 · 没法用
~10k-30kBERT (30k) · Llama-2 (32k)序列适中 · 中文不友好
50k-65kGPT-2 (50k) · Mistral (32k 也算这档)英文舒适
100k-150kGPT-4 / Llama-3 / Qwen多语言 + 长上下文友好
200k+少见 · 多用于多语言模型embedding 矩阵巨大

vocab 对参数的影响

embedding + lm_head（不 tie）：2 · vocab · n_embd

tie 之后：vocab · n_embd

例：Llama-3 8B · vocab=128k · n_embd=4096 → emb 占 524M · 总参 8.0B 的 6.5%。
但小模型 (350M · n_embd=1024) · vocab=128k → emb 占 131M · 占 37%！

规律：模型越小 · vocab 在总参里占比越大。所以小模型常砍 vocab（30k 左右） · 大模型才舍得开 100k+。

选 vocab 的实操步骤

  1. 盘清你必须支持的语言。纯英文 30-50k 够。中英混 100k 起。
  2. 盘清你的 base model。继续训现成 base · 必须沿用它的 tokenizer · 不能换。
  3. 新训 base · 跑实验：在你的真实语料上分别试 30k / 50k / 100k · 看 token rate · 平均一个 token 多少 byte。
  4. 2 byte/token 以下都能接受。低于 1.5 说明 vocab 偏小。

10 · Tokenizer 怎么接进 phase 1 nanoGPT

phase 1 nano/data.py 是 char-level · 现在我们想把它升级到 BPE-level 怎么办？三处改动 + 一处不变：

改 1 · CharDataset → BPEDataset

# 原：char-level
ids = np.array([self.stoi[c] for c in self.text], dtype=np.int64)

# 新：BPE
from nano.bpe import BPE
bpe = BPE.load("data/tokenizer/nano-bpe.json")
ids = np.array(bpe.encode(self.text), dtype=np.int64)

改 2 · vocab_size 来自 tokenizer

model_cfg = GPTConfig(
    vocab_size=bpe.vocab_size,   # 1024 而非 65
    block_size=cfg.block_size,
    ...
)

改 3 · sample.py 用 BPE encode/decode

idx = torch.tensor([bpe.encode(args.prompt)], dtype=torch.long, device=device)
out_ids = model.generate(idx, ...).tolist()[0]
print(bpe.decode(out_ids))

不变 · GPT 模型本身

nano/gpt.py 一行不用改。GPT 只关心 vocab_size 和 id 序列 · tokenizer 长什么样它根本不知道。这就是抽象的力量。

为什么我们 phase 2 没真的换上去

shakespeare 1MB 太小 · char-level 已经够用 · 换 BPE 收益小 · 反而把代码复杂度抬上去。 phase 3 (pretrain) 我们会真用 BPE · 那时候语料是 100MB+ · char-level 序列长得训练成本爆炸。
