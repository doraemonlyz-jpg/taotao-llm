1 · Pretrain 是什么 · 跟 SFT / RLHF 的关系

训练一个现代 LLM 通常分三段（Llama / GPT / Qwen / DeepSeek 都这样）：

阶段数据目标占总成本本书 phase
Pretrain1-15T token · 网页 / 书 / codenext-token 预测~95%本书 (3)
SFT10k-1M 条对话"会聊天 / 听指令"~3%4
Preference (DPO/RLHF)10k-100k 偏好对对齐人类喜好~2%6

Pretrain 是地基。它决定模型有多聪明 · 知道多少世界知识 · 中英能力强不强。SFT 和 DPO 只是"教礼仪" · 不会让一个不读书的模型变聪明。

本书的 toy 实验

我们在 TinyStories（200 万条 GPT-3.5 生成的儿童故事 · ~500MB）上训 10M 参数的 baby GPT。 TinyStories 的妙处：词汇受限 · 句法简单 · 10M 参数 + 10M token 就能学到语法 + 简单叙事。 比直接上 FineWeb（45TB · 大模型才学得动）适合 Mac 学习。

2 · Data is everything · FineWeb 的故事

2024 年最重要的 LLM 论文之一不是模型架构 · 是 HuggingFace 出的 FineWeb · 一个 15T token 的开源 web 语料。 他们的关键贡献：用同样的模型架构、同样的算力 · 仅仅换了清洗策略 · pretrain 后的模型在所有 benchmark 上比 RedPajama / Dolma 高 5-10 个点。

规律

到 2024 年 · 大家公认：data quality > data quantity > model size > training time。 你能找到的 5 个 trick 里 · 4 个跟数据有关。

FineWeb 的清洗 pipeline

  1. language ID：fastText 跑一遍 · 只留你想要的语言
  2. quality classifier：用一个小分类器打分 · 过滤垃圾页
  3. deduplication：MinHash + LSH · 全集近重复去掉 (能去 60%+)
  4. repetition filter：连续重复字符 / 行 / n-gram 多的页面扔掉
  5. perplexity filter：拿小 LM 打分 · 删掉 ppl 太高的乱码页
  6. safety / PII：URL 黑名单 + 简单 PII 模式

本书没做这些 · 因为 TinyStories 已经是清洗好的

TinyStories 是 GPT-3.5 生成的 · 词汇受限 · 句法干净。直接用就行。 真做 web 数据 pretrain · 上面 6 步至少占工程量的 60% · 而且每一步都需要 跑数据反复看 sample。

3 · tokenize-then-pack · 为什么要做 .bin 缓存

看 industrial/pretrain/data.py 里 PretrainDataset.prepare()。 做的事：流式拉 HF 数据 → 每条 tokenize → 拼 stream → 写 .bin。一次准备 · 永远复用。

不缓存的代价

HF 的 tokenizers Rust 版极快 · 但 1B token 还是要 10-30 分钟。 如果训练时每个 batch 现 tokenize · 你的 dataloader 会变成瓶颈 · GPU 一直在等 CPU。
缓存到 .bin · 训练时直接 np.memmap · 几乎零开销。

.bin 的结构

就一个连续的 token id 数组。dtype 看 vocab：

vocabdtypebyte/token1B token 占盘
≤ 65535uint1622 GB
≤ 4.3Buint3244 GB

看 industrial/pretrain/data.py：

dtype = np.uint16 if vocab_size < 2**16 else np.uint32
arr = np.asarray(buf, dtype=dtype)
arr.tofile(f)              # 顺序写
# 训练时
ids = np.memmap(d / "train.bin", dtype=dtype, mode="r")

memmap 是关键 trick：操作系统按需把磁盘页映射到内存 · 不真把 10GB 全读到 RAM。 你拿一个 batch · 就只触发那几页的读入。

4 · Packing · 文档间的 EOS 分隔

训练时一个 batch 是 (B, T) · T 是 block_size。但单条文档可能：

  • 太短（推特 / 短回复）：浪费 padding 空间
  • 太长（书 / 长论文）：截断 / 放不下

解决：把所有文档拼成一条超长 stream · 每条之间加 EOS · 然后随机切 (B, T) 窗口。这就是 packing。

# industrial/pretrain/data.py 的 _tokenize_and_pack
for example in stream:
    ids = tok.encode(example["text"], add_special_tokens=False)
    buf.extend(ids)
    buf.append(eos_id)        # ← 这一行 · 文档边界
    ...

# 训练时随机抽窗口
ix = np.random.randint(0, len(ids) - block_size - 1, size=(batch_size,))
x = np.stack([ids[i : i + block_size] for i in ix])

为什么要 EOS 分隔

不加 EOS · 模型会学到 "前一篇文档结尾" → "下一篇文档开头" 的虚假关联。 加 EOS · 模型学到的是 "看到 EOS 就 reset 注意力" · 行为更干净。 推理时也用 EOS 做 stop signal · 训练推理一致。

跨边界 attention 怎么办

朴素 packing 下 · 一个 (B, T) 窗口可能横跨 3 篇文档。前两篇文档结尾能看到下一篇文档开头 (causal mask 不限边界)。 有几种处理：

策略实现谁用
不管不做特殊处理 · EOS 自然让模型学会 reset大多数 · 包括 GPT-2 / Llama
document mask在 attention 里禁止跨 EOS · attention 多一层 maskReformer · 一些研究模型
example packing记录边界 · 用 attention bias 隔离FlashAttention 2 支持

本书 nano + industrial 都用第一种。简单 · 主流 · 实测损失可忽略。

5 · effective batch size · 梯度累积的几何

训 LLM 你会反复看到 "batch size 1024 · global batch size 4M tokens"。这两个是什么关系？

公式

effective batch tokens = micro_batch_size × grad_accum_steps × block_size × world_size

例：micro=16 · accum=4 · block=512 · 1 GPU → effective = 16×4×512×1 = 32,768 tokens / step

为什么不直接把 micro_batch 调到 64 · 干掉 accum？答案：显存不够。 单次 forward + backward 的显存占用大概是：

  • activations: O(B · T · L · C) · linear 每层一份 · 这是大头
  • params + optimizer state: O(参数量 × 6) (AdamW: 1 weight + 2 momentum + 2 grad + 1 buffer)

当 micro_batch × T 超过显存上限 · 就 OOM。grad accum 让你省显存换计算时间：

# industrial/pretrain/train.py 的核心
optim.zero_grad()
for _ in range(grad_accum_steps):
    xb, yb = ds.get_batch(...)
    _, loss = model(xb, yb)
    loss = loss / grad_accum_steps    # 关键 · 让累积梯度的尺度对
    loss.backward()                    # 不 zero_grad · 梯度自动相加
optim.step()                           # 只在 accum 完成后更新

本书的设置

industrial/pretrain/train.py 默认 micro=16 · accum=4 · block=512 → effective batch = 32,768 tokens。 GPT-2 论文 effective batch ≈ 524,288 tokens · 是我们 16×。但教学项目这样足够看到 loss 平滑下降。

6 · Mixed precision · MPS 的限制

精度位动态范围显存MPS 支持建议
fp323210⁻³⁸ ~ 10³⁸baseline✓ 完美本项目默认
fp161610⁻⁵ ~ 65k0.5×不稳 · loss → nanMac 上别用
bfloat161610⁻³⁸ ~ 10³⁸0.5×M2+ 支持云上 + GPU 选这个
fp88更窄0.25×不支持H100 / B200 才有意义

为什么 bf16 比 fp16 更稳

fp16 的指数位只有 5 bit · 表示范围 10⁻⁵ ~ 65k。 LLM 训练时偶尔出现 large activation · 直接溢出 nan。 bf16 指数位 8 bit (跟 fp32 一样) · 范围跟 fp32 同 · 只是精度低。 对深度学习几乎免费午餐 · 因为深度学习的瓶颈是动态范围 · 不是 mantissa 精度。

MPS 现状 (2026)

PyTorch MPS 后端正在补齐 bf16 支持 · 但还有边角 case 出问题。 本项目 MPS 默认 fp32 · 训练慢 30-50% · 但稳。 如果你在云上跑 H100 · 改用 torch.cuda.amp.autocast(dtype=torch.bfloat16) 即可。

7 · LR schedule at scale

跟 phase 1 nano-train 用的同一个 cosine + warmup · 但有几个 scaling 时的细节：

规模warmuppeak lrmin lr
nanoGPT (本书)200 步6e-46e-5
GPT-2 small (124M)2000 步 (~10M token)6e-46e-5
GPT-3 175B~375M token6e-56e-6
Llama-2 70B2000 步1.5e-41.5e-5
Llama-3 405B8000 步3e-43e-5

经验

peak lr 跟 batch size 大致成 √ 比例：batch ×4 → lr ×2。 实际项目里别太迷信公式 · 跑 3 个 lr 看 loss 曲线 · 选最低的那个。

看代码

# nano/train.py 的 get_lr · industrial 复用
if it < warmup_iters:
    return lr * (it + 1) / warmup_iters
progress = (it - warmup_iters) / max(1, max_iters - warmup_iters)
coeff = 0.5 * (1 + cos(π * progress))
return min_lr + coeff * (lr - min_lr)

cosine 的好处：训练末尾 lr 自然趋近 min_lr · 模型可以做精细调整。 对比 linear decay 在末尾 lr 突然归 0 · 容易在末段过拟合。

8 · Chinchilla · scaling law · N × D 的甜点

2022 年 DeepMind 发了 Chinchilla 论文 · 终结了 "越大越好" 的盲信仰。

Chinchilla 经验律

给定算力 C (FLOPs) · 最优配置满足：

\[ N_{opt} \cdot D_{opt} \approx \frac{C}{6}, \quad N_{opt} \approx D_{opt} \cdot 5 \]

翻译：每个参数应该看 ~20 个 token。

模型params Ntokens DD / N评价
GPT-3 (2020)175B300B1.7严重欠训 · 被 Chinchilla 打脸
Chinchilla 70B70B1.4T20正合甜点
Llama-2 7B7B2T286故意过训 · 推理省成本
Llama-3 8B8B15T1875极端过训 · 数据是稀缺资源
本书 tiny10M10M1欠训 · 但 toy 不在乎

2024+ 的新共识

Chinchilla 假设 "训练算力 = 推理算力" · 但现实里推理是反复跑的。 过训小模型（Llama-3 那种 D/N=1000+）成本最优 · 因为推理时省更多。 本书的 toy 不考虑这个 · 但你做生产时要记住。

跑你自己的 mini scaling law

scripts/scaling_law.py 有一个 6-run 网格 (tiny/mini × 200/600/1500 iters)：

uv run python scripts/scaling_law.py --quick

跑完看 data/scaling/results.html：你应该看到 (a) 同样 iters 下 mini 比 tiny loss 低 · (b) 同样 size 下 iters 越多 loss 越低 · 但 (c) 收益递减。这就是 scaling law 的低维投影。

9 · Loss spikes · 调试方法

训 LLM 你会遇到这种曲线：loss 平稳下降 · 突然某步暴涨 100x · 然后慢慢恢复（或炸成 nan 不归来）。 这就是 loss spike · LLM 训练老朋友。

常见原因

原因判断解
学习率太大spike 集中在 warmup 后峰值期lr 砍 1/2 · warmup 加倍
梯度炸掉spike 时 |grad| 突然 100+grad_clip 调低 · 0.5 / 0.3 · 用 mixed precision 时尤其
数据有脏同一 batch 反复 spikedump 那个 batch · 看是不是乱码 / 极长重复
fp16 溢出weight / activation 突然 inf换 bf16 或 fp32
Adam ε 太小变量爆炸时 1/sqrt(v+ε) 不稳ε 从 1e-8 调到 1e-5

预防

  • 每 N 步存一个 ckpt · spike 后能 rollback
  • 定期 log |grad| 和 lr · 让 spike 可视
  • 关键：spike 后先看是不是数据问题 · 80% 是数据 · 不是模型

本书代码里的预防

industrial/pretrain/train.py 每步都 log |grad| · grad_clip=1.0 · 默认 fp32 · 这三件事消除了 90% 的 spike。

10 · Checkpoint resumption · 断点续训

训 1B 模型一周不停机？不可能。机器会重启 · jupyter 会断 · 你会想换学习率。 所以训练必须能从中断处接着跑。

要存什么

状态不存的后果
model_state_dict白训
optim_state_dictAdam 的 m / v 重置 · loss 立刻反弹
iter 计数lr scheduler 错位
scheduler statelr 错位 (scheduler 是无状态的可不存)
RNG state同样 batch 顺序无法复现 · 可选
data 指针下次会重看一遍 epoch · 可选

看代码

# industrial/pretrain/train.py 的 _save_ckpt
torch.save({
    "model_state": model.state_dict(),
    "optim_state": optim.state_dict(),
    "model_cfg": asdict(model.cfg),
    "train_cfg": _serialise_cfg(cfg),
    "iter": state.iter,
    "best_val": state.best_val,
}, path)

# resume 时
if cfg.resume and ckpt.exists():
    blob = torch.load(ckpt, map_location=device, weights_only=False)
    model.load_state_dict(blob["model_state"])
    optim.load_state_dict(blob["optim_state"])
    state.iter = blob["iter"]
    state.best_val = blob["best_val"]

怎么用：

uv run python -m industrial.pretrain.run train --max-iters 1000      # 第一次
# Ctrl-C 杀掉
uv run python -m industrial.pretrain.run train --max-iters 3000 --resume   # 接着训

11 · RoPE 预告 · phase 8 详讲

本书的 model 还用着 phase 1 的 learned absolute position embedding · 这是 GPT-2 的老配方。 2022 后所有现代 LLM (Llama / Qwen / Mistral / DeepSeek) 都换了 RoPE (Rotary Position Embedding)。

RoPE 一句话

不再加位置 embedding · 而是把 query 和 key 向量按位置 t 旋转一个角度 · 让 attention 自带相对位置感。

\[ q_t = R_t \cdot q, \quad k_t = R_t \cdot k \] \[ q_t^\top k_s \;\propto\; (R_{t-s} q)^\top k = \text{相对位置依赖}\]

为什么要换

RoPE 的好处说明
外推训 4k context · 推理塞 32k 还能勉强用
长上下文友好NTK / YaRN scaling 方案都基于 RoPE
无参数不占 embedding 矩阵 · 省参数

实现只需要 30 行 PyTorch。phase 8 (infra) 我们会给 nano/gpt.py 加 RoPE 选项。
